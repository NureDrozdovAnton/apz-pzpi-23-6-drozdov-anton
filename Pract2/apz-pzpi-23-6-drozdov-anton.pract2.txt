3 ОПИС ВИКОНАНОЇ РОБОТИ
        3.1 Загальні відомості про систему
        Назва системи: Figma
        Розробник: Figma Inc.
        Призначення системи:
* Область застосування: Хмарний інструмент для дизайну інтерфейсів (UI/UX), прототипування та спільної роботи в реальному часі.
* Користувачі: UI/UX-дизайнери, продуктові менеджери, фронтенд-розробники, маркетологи.
* Основні функції: Векторне редагування графіки, створення інтерактивних прототипів, спільне редагування макетів у реальному часі (multiplayer mode), інспектування коду для розробників, система компонентів та дизайн-систем.
        3.2 Архітектурний стиль системи
Figma використовує гібридну архітектуру, яка поєднує кілька стилів:
1. Клієнт-центрична архітектура з "товстим клієнтом" (Thick Client): Основна логіка рендерингу та обробки векторної графіки винесена на сторону користувача.
2. Подієво-орієнтована (Event-Driven) / Multiplayer: Зміни в документі транслюються як потік подій (операцій) між клієнтами через центральний сервер синхронізації.
3. Мікросервісна (на бекенді): Допоміжні функції (авторизація, плагіни, експорт файлів, коментарі) винесені в окремі мікросервіси.
Класична клієнт-серверна модель (де сервер рахує графіку і віддає картинку) не здатна забезпечити 60 FPS при редагуванні важких макетів. Перенесення графічного рушія в браузер прибрало затримку (latency). Подієва модель необхідна для того, щоб користувачі бачили курсори та зміни один одного миттєво.
3.3 Основні компоненти системи
Інтерфейс користувача:
* React App: використовується лише для зовнішньої обгортки - панелі інструментів, шари, налаштування шрифтів.
* Власний графічний рушій на С++: компілюється у WebAssembly (WASM). Він малює макет на елементі canvas за допомогою WebGL. Це дозволяє Figma працювати зі швидкістю десктопного додатка безпосередньо у браузері.
        Серверна частина:
* Multiplayer Server (написаний на Go): Високопродуктивний сервер, який тримає постійні з'єднання з клієнтами. Його єдине завдання - швидко пересилати операції редагування від одного користувача всім іншим, хто відкрив той самий файл.
* REST API / Web-сервери (написані на Ruby on Rails / Go): Обробляють стандартні запити: завантаження списку проєктів, авторизація, керування командами.
        Рівень бізнес-логіки:
* На клієнті: Розв'язання конфліктів редагування. Коли двоє людей одночасно рухають один квадрат, клієнтський рушій обробляє це локально за допомогою алгоритмів синхронізації, мінімізуючи запити до сервера.
* На сервері: Валідація прав доступу до файлу та координація "кімнат" (документів).
        Рівень зберігання даних:
* Amazon S3: Тут зберігаються безпосередньо файли дизайну у власному бінарному форматі (це "знімки" або snapshot стану документа), а також завантажені користувачами зображення.
* PostgreSQL: Зберігає реляційні дані: користувачів, команди, метадані про проєкти, права доступу та коментарі.
* Redis: Використовується для швидкого збереження поточного стану активних сесій (хто зараз онлайн у якому файлі).
        Допоміжні сервіси:
* Сервіс експорту (Export Service): Окремий ізольований сервіс, який рендерить векторні макети в PNG/SVG/PDF на сервері, щоб не навантажувати комп'ютер користувача.
* Сервіс плагінів: Ізольоване середовище (Sandbox) всередині браузера для безпечного виконання стороннього коду користувачів.
3.4 Взаємодія компонентів
Потоки даних та протоколи
* Ініціалізація: Користувач відкриває посилання -> Запит йде по HTTPS (REST API) -> Повертаються метадані та snapshot файлу з Amazon S3. WebAssembly-рушій завантажує цей файл у пам'ять браузера і рендерить макет.
* Спільна робота (Multiplayer): Користувач А пересуває коло -> Подія пакується в компактний бінарний формат і летить через WebSocket (WS) протокол на Multiplayer Server -> Сервер миттєво пересилає цю подію користувачу Б через його WebSocket -> Рушій користувача Б оновлює коло на екрані.
        Механізми синхронізації
Figma використовує централізовану схему синхронізації (на відміну від чистих CRDT алгоритмів, як у Google Docs). Сервер Go виступає "джерелом істини". Він присвоює кожній операції порядковий номер. Якщо виникає конфлікт (два користувачі одночасно змінили колір), сервер приймає ту операцію, яка прийшла першою, а другий клієнт коригує свій локальний стан під рішення сервера.
На рисунку 1 за допомогою діаграми послідовності зображено механізм синхронізації:
1. User_A переміщує об'єкт. Локальний рушій відмальовує дію миттєво (0 затримки для User_A).
2. User_A відправляє повідомлення MoveObject(id, x, y) через WebSocket до Multiplayer_Server.
3. Multiplayer_Server фіксує зміну, оновлює стан документа в оперативній пам'яті та транслює повідомлення UpdateObject(id, x, y) через відкритий WebSocket до User_B.
4. User_B отримує повідомлення, його WebAssembly-рушій перераховує координати та перемальовує об'єкт на Canvas.

3.5 Масштабованість та надійність
* Механізми балансування навантаження: Використовуються AWS ALB (Application Load Balancers). Для Multiplayer-серверів застосовується балансування на основі ідентифікатора файлу (File ID Routing): користувачі, які працюють над одним і тим самим файлом, завжди спрямовуються на один і той самий конкретний сервер (або кластер), щоб мінімізувати затримку синхронізації.
* Відмовостійкість: Якщо один Multiplayer-сервер падає, клієнти автоматично перепідключаються через WebSockets до іншого. Новий сервер швидко викачує останній snapshot файлу з S3, застосовує останні зміни з логу подій і відновлює сесію.
* Кешування: Figma агресивно кешує код WebAssembly та статичні елементи дизайну в браузері (через Cache API). На серверній частині Redis кешує права доступу та метадані, щоб не перевантажувати PostgreSQL.
* Реплікація: База даних PostgreSQL працює в режимі Multi-AZ (кілька зон доступності) в AWS з Primary сервером для запису та Replica серверами для читання. Файли в S3 автоматично реплікуються між різними дата-центрами.
* Контейнеризація та хмара: Бекенд повністю розгорнутий в Amazon Web Services (AWS) з використанням Docker-контейнерів та оркестрації (ECS/Kubernetes) для автоматичного горизонтального масштабування вебсерверів залежно від трафіку (наприклад, у робочі години дизайнерів).
