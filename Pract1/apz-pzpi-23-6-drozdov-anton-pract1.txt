3 ОПИС ВИКОНАНОЇ РОБОТИ
        3.1 Загальні відомості про патерни проєктування
        Патерни проєктування - це архітектурні рішення поширених проблем, які виникають при проєктуванні та розробці програмного забезпечення. Це не готовий код, а шаблон (концепція) вирішення задачі, який можна адаптувати під конкретну проблему та реалізувати різними мовами програмування.
        Вони необхідні для економії часу, стандартизації коду, а також для підтримки кодової бази і подальшого розвитку.
        Класифікація GoF виділяє 3 великі групи:
* породжувальні (creational): створення об’єктів без безпосередньої ініціалізації, роблячи систему незалежної від способу створення об’єктів;
* структурні (structural): формування великих та гнучких структур;
* поведінкові (behavioral): організація ефективної взаємодії та розподілу обов’язків між об’єктами.
Патерни GoF застосовуються при об’єктно-орієнтованому програмуванні, вони вирішують проблеми взаємодії об’єктів та класів у кодовій базі.
        3.2 Опис патерна Стратегія (Strategy)
* Назва патерна: Стратегія (Strategy).
* Тип патерна: поведінковий (behavioral).
* Основне призначення: патерн визначає сімейство схожих алгоритмів, інкапсулює кожен з них в окремий клас і робить їх взаємозамінними. Це дозволяє вибирати та змінювати алгоритм прямо під час виконання програми, незалежно від клієнта, який цей алгоритм використовує. Патерн позбавляє від громіздких умовних операторів та відокремлює логіку виконання від контексту.
* Передумови застосування: використання патерну є доцільним, якщо існує кілька споріднених класів, які відрізняються лише своєю поведінкою маючи однаковий інтерфейс; якщо потрібно мати різні варіанти алгоритму для вирішення однієї конкретної задачі; якщо алгоритм містить складну логіку, яку треба приховати від клієнтського коду (інкапсуляція).
* Переваги: дозволяє позбутися складних розгалужень (if-else/switch) даючи більш чистий код; дозволяє додавати нові стратегії (алгоритми) в систему не змінюючи код існуючих стратегій чи класу контексту; ізоляція логіки; динамічність (можливість змінювати поведінку об’єкта).
* Недоліки: усі стратегії використовують один інтерфейс, тому ряд стратегій можуть отримувати надлишкові параметри, які не використовуються самим алгоритмом; якщо алгоритмів небагато і вони майже не змінюються, використання патерна лише ускладнить архітектуру;
3.3 Структура патерна
Опис структурних частин:
* Контекст (Context):
   * клас, який зберігає посилання на одну з конкретних стратегій через загальний інтерфейс;
   * не знає, яка саме стратегія зараз обрана;
   * викликає метод стратегії;
   * надає клієнту метод для зміни стратегії.
* Інтерфейс стратегії (Strategy Interface):
   * спільний інтерфейс (або абстрактний клас) для всіх варіантів алгоритмів;
   * оголошує мето, який Конекст використовує для виконання алгоритму.
* Конкретні стратегії (Concrete Strategies):
   * класи, які безпосередньо реалізують інтерфейс стратегії;
   * кожен клас містить свою, унікальну версію алгоритму.
        Опис взаємодії об’єктів.
        Взаємодія між об’єктами відбувається за такою схемою:
1. Ініціалізація: клієнт створює об’єкт Контексту та передає йому об’єкт однієї з Конкретних стратегій.
2. Запит на виконання: коли програмі потрібно виконати завдання, Клієнт звертається до Контексту, викликаючи певний метод.
3. Делегування: Контекст не вирішує задачу сам, а перенаправляє виклик до об’єкта Стратегії, який на той момент записаний у ньому.
4. Динамічна зміна: при зміни умов, Клієнт може передати в Контекст іншу Конкретну стратегію і наступний виклик метода виконає вже новий алгоритм.
UML-діаграми з поясненнями.
  

Рисунок 1 - UML-діаграма патерну
Діаграма відображає відношення між учасниками:
* Контекст має Стратегію (агрегація);
* Конкретна стратегія реалізує Стратегію.
        Відношення між Клієнтом та Стратегією (не зображено на діаграмі) може бути агрегацією або композицією.
3.4 Реалізація патерна
Опис реалізація мовою програмування Rust.
Створення базових інтерфейсів - створюємо трейт (trait), який є Інтерфейсом стратегії і описує, які методи повинні бути реалізовані кожної конкретною стратегією.
1 pub trait ShippingStrategy {
2     fn calculate_cost(&self, weight: f64, distance: f64) -> f64;
3 }
Реалізація конкретних класів - визначаємо три структури (в мові програмування Rust вони виконують функції класів), а саме: NovaPostShipping, UkrPostShipping, SelfPickupShipping та реалізуємо Інтерфейс стратегії для кожної конкретної стратегії.

Демонстрація використання - визначаємо структуру Контекст - структуру Order. Додаємо методи для виконання бізнес-логіки, для зміни стратегії та конструктор. Використовуємо інструмент мови Box для динамічної диспетчеризації для підтримки зміни стратегії під час виконання програми. Створюємо функцію main для використання та демонстрації роботи.
1 pub struct Order {
2     weight: f64,
3     distance: f64,
4     shipping_strategy: Box<dyn ShippingStrategy>,
5 }
6 
7 impl Order {
8     pub fn new(weight: f64, distance: f64, strategy: Box<dyn ShippingStrategy>) -> Self {
9         Self {
10             weight,
11             distance,
12             shipping_strategy: strategy,
13         }
14     }
15 
16     pub fn set_strategy(&mut self, strategy: Box<dyn ShippingStrategy>) {
17         self.shipping_strategy = strategy;
18     }
19 
20     pub fn calculate_shipping(&self) -> f64 {
21         self.shipping_strategy.calculate_cost(self.weight, self.distance)
22     }
23 }
24

26     let mut order = Order::new(10.0, 100.0, Box::new(NovaPostShipping));
27          println!("Нова Пошта: {:.2} грн", order.calculate_shipping());
